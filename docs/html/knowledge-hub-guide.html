Knowledge Hub · 双项目上手导学

一套「企业知识库」的完整实现：把散落在 PDF / Word / Excel / PPT 里的制度文档收进来，解析成 Markdown、按权限发布， 再同时建立全文索引 / 向量索引 / 知识图谱三套检索能力，最后用 Agentic RAG 提供「问一句、给答案、附出处」的问答。 后端 240+ 个 TS 文件，前端 React 19 + Ant Design 6。

knowledge-hub-backend

NestJS 11 单体服务，无全局路由前缀，端口 3000。承载全部业务：认证权限、文档域、索引管线、混合检索、RAG 问答、知识图谱。

NestJS 11TypeORM + Postgres Mongoose + MongoElasticsearch 8 Neo4j 6RabbitMQ LangChain 
cd knowledge-hub-backend
docker compose up -d      # 起 7 个基础设施容器
cp .env.example .env      # 至少填 OPENAI_API_KEY
pnpm install
pnpm start:dev            # http://localhost:3000

knowledge-hub-frontend

React 19 + Vite 8 + Ant Design 6 单页应用，端口 5173。/api 前缀由 Vite 代理转发到后端 3000 并去掉前缀。

02架构与存储分工

每个存储只干最擅长的事，这是本项目最重要的设计取舍。理解这张表，后面所有代码都能对上号。

组件存什么为什么是它
PostgreSQL文档元数据、审核流水、用户/角色/权限、团队、AI 会话（12 张表）需要事务、外键、条件分页的结构化数据
MongoDB文档 Markdown 正文（document_content）长文本、无需 join、按 document_id 单点读写
Elasticsearchkh_chunk（分块 + 1024 维向量）、kh_document（文档级全文）中文 IK 分词 + kNN 向量检索
Neo4j文档 / 块 / 实体节点与关系「实体 A 与实体 B 什么关系」这类多跳问题
Redis激活 token、重置验证码、对话短期记忆热窗口短 TTL 一次性数据 + 高频读写
RustFS (S3)PDF 抽取的图片、原文件二进制对象不适合塞进数据库
RabbitMQ发布后的三条索引管线消息建索引耗时长（embedding + LLM 抽取），必须异步
贯穿全项目的约束：Postgres 与 Mongo 是两个独立库，没有跨库事务。 写正文采用「先写 Mongo → 再写 Postgres → 失败则补偿删除 Mongo」，只能保证最终一致。

认证与权限：三个全局 Guard

1 天核心纯逻辑，最好入门
✓
›
目标：搞懂一次请求如何被三个全局守卫依次放行 / 拦截；权限从哪来；前端如何用权限码控制菜单与按钮。

核心机制

请求 ──► JwtAuthGuard ──► RolesGuard ──► PermissionsGuard ──► Controller
        （是否登录）      （@Roles）      （@RequirePermission）
             标了 @Public() 的接口跳过登录校验

用户最终权限 = 直授权限 kh_user_permission
             OR （kh_user_role → kh_role_permission）
             （ROLE_ADMIN 额外并入 ADMIN_OPERATION_PERMISSIONS）

角色只有三个：ROLE_ADMIN / ROLE_REVIEWER / ROLE_USER
权限码分三级：菜单 / 按钮 / 接口，如 document:list、document:create、system:permission:edit

状态机（src/document/document-status.ts，纯函数，好测）

   │ 草稿    │ ─────► │  待审核        │ ────────► │  已发布      │
   │ Draft 0│        │ PendingReview 3│           │ Published 1 │
   └───┬────┘        └───────┬───────┘           └──────┬──────┘
       │   ▲   驳回回到草稿    │                          │ 归档
       │   └──────────────────┘                          ▼
       │                                        ┌─────────────┐
       └────────── 下架编辑（回到草稿）──────────► │  已归档      │
                                                │ Archived 2  │

canSubmitReview  只有草稿/已发布/已归档可提交审核（已发布再提审会先清索引）
canEditContent   待审核期间禁止改正文（防「审的内容」与「发布的内容」不一致）
canArchive       只有已发布可归档
DOCUMENT_REQUIRE_APPROVAL  是否走审核（默认 true）

可见性规则（src/document/document-access.ts，规则只写一次）

可读 = 管理员/审核员（unrestricted）
     OR 文档作者是自己
     OR （已发布 AND（文档公开 OR 文档 team_id IN 我的团队集合））

可写 = 管理员 OR 文档作者

同一套规则下推到三处查询：
  Postgres   → QueryBuilder 拼接条件
  Elasticsearch → esVisibilityFilter() 生成 bool.should，再由 wrapEsQuery()
                  把「相关性放 must、权限放 filter」，保证权限条件不影响打分
  Neo4j      → neo4jDocumentAccessWhere() 生成 Cypher 条件 + neo4jAccessParams() 传参

异步索引管线：MQ 三路队列

1 天进阶可视化强
✓
›
目标：理解「发布」为什么是异步的；三路队列各干什么；如何观察「最终一致」这个现象。

发布 → 索引 的异步链路

DocumentService.publish()免审直接发布，或审核通过后触发
↓
DocumentPipelinePublisher投递三条消息到 RabbitMQ
↓
rag.reindex清旧块 → 分块(512/64) → 批量 embedding → ES kh_chunk
search.index只带 documentId，消费者回查 PG + Mongo → ES kh_document
kg.graph分块 → LLM 抽实体关系 → Neo4j
↓
PipelineOrchestrator逐篇 try/catch，单篇失败不影响其它文档
设计要点
1. Search 消息只携带 documentId，正文在 Mongo 由消费者自己回查 —— MQ 里不塞大文本
2. 重建前先清旧块 deleteByDocId，重复发布不产生脏数据
3. 可见性变更走专用分支 updateVisibility：只更新三套索引上的
   is_public / team_id，不重跑 embedding 与实体抽取
4. ES / Neo4j 不可用时由 ELASTICSEARCH_ENABLED / NEO4J_ENABLED 控制降级跳过

  • src/mq/mq.constants.ts3 个交换机 + 3 个队列 + 路由键的全貌
  • src/mq/document-pipeline.publisher.ts / document-pipeline.consumer.ts生产与消费两端
  • src/pipeline/chunking.service.ts512/64 分块 + 标题前缀

混合检索：双路召回 + RRF + rerank

1 天核心调参可玩性高
✓
›
目标：搞懂关键词召回 + 向量召回 → RRF 融合 → rerank 精排的完整链路，以及每一步的降级策略。
query
  ├─► 关键词召回（ES kh_chunk）  ┐  multi_match:
  │     document_title^2, content │  analyzer ik_smart
  └─► 向量召回（ES kh_chunk kNN） ┘  1024 维 cosine
        │  双路并行，各取 RAG_HYBRID_TOP_K=20
        ▼
  RRF 融合（RAG_RRF_C=60）   score = Σ 1 / (k + rank)
        ▼
  rerank 精排（qwen3-rerank）→ 丢弃低于 RAG_MIN_SCORE=0.4 的块
        ▼
  ChunkHit[] { chunkId, documentId, documentTitle, content, heading, score }

降级策略（关键依赖挂了也能用）
  Embedding Key 未配置   → 使用本地哈希向量
  向量化失败            → 跳过向量路，退化为纯关键词检索
  Rerank 不可用/失败     → 直接返回 RRF 融合顺序

必读文件

  • src/ai/hybrid-retrieval.service.ts ★双路召回 → RRF → rerank 的编排中枢
  • src/pipeline/vector-index.service.tsES kh_chunk 的写入 / kNN / 关键词 / RRF / 可见性构造
  • src/pipeline/search-index.service.tsES kh_document 文档级全文索引 + 高亮分页
  • src/ai/reranker.service.tsqwen3-rerank 精排 + 阈值过滤
  • src/search/POST /search 文档级全文检索

Apipost 验证 · 计划「P4 · 混合检索对比」

  1. 同一个 query 分别调 POST /search（文档级，带 IK 高亮）与 POST /rag/search（块级混合检索，不调 LLM），对比返回粒度。
  2. 改 .env 里的 RAG_HYBRID_TOP_K / RAG_RRF_C / RAG_MIN_SCORE，重启后端再调，观察结果条数与排序变化。
  3. 把 EMBEDDING_API_KEY 留空重启，观察检索质量下降（走本地哈希向量）但仍可用。
动手理解 RRF：某块在关键词路排第 2、向量路排第 5，则得分 1/(60+2) + 1/(60+5)。RRF 的价值是不需要两路分数可比，只看排名。

CApipost 实战：把接口调试变成肌肉记忆

这个项目没有 Swagger，验证全靠 curl-*.md。用 Apipost 建一套可复用的调试环境，能把每一阶段的学习成本压到最低。 下面 5 步做完，你就有了一个「一键登录、一键跑发布链路」的工作台。

  1. 建项目与环境

    新建项目 Knowledge Hub，再新建环境 本地，定义三个变量：

    baseUrl       http://127.0.0.1:3000
accessToken   （先留空，登录后自动写入）
refreshToken  （先留空）
    注意：后端的 baseUrl 就是 http://127.0.0.1:3000 本身。/api 前缀是前端 Vite 代理加的，直连后端时不要带。

  2. 调通登录并自动提取 token

    新建 POST {{baseUrl}}/auth/login，Body 选 JSON： 

    { "username": "admin", "password": "123456" }

    在后置脚本里写入环境变量，之后所有接口都能复用：

    const res = apt.response.json();

if (res && res.accessToken) {
  apt.environment.set("accessToken", res.accessToken);
  apt.environment.set("refreshToken", res.refreshToken);
  console.log("token 已写入，过期时间(秒):", res.expiresIn);
}

    返回结构：{ accessToken, refreshToken, tokenType, expiresIn, userInfo }。换 reviewer / user 账号重跑即可切换身份。

  3. 给项目挂上统一鉴权

    在项目级「公共参数 / 请求头」里加一条，所有接口自动带上，不用逐个填： 

    Key:    Authorization
Value:  Bearer {{accessToken}}
    验证方法：调 GET {{baseUrl}}/auth/me，能看到 permissions 数组即成功。 access token 只有 2 小时有效，过期后调 POST /auth/refresh（body 传 {"refreshToken":"{{refreshToken}}"}）刷新。

  4. 建「执行流」跑通发布链路

    把 Phase 2 的那串接口按顺序编排成一个执行流，用响应提取把 documentId、taskId 串起来，以后一键重跑： 

    ① POST  /auth/login                      → 提取 adminToken
② POST  /documents                       → 提取 docId（创建草稿）
③ POST  /documents/{{docId}}/reviews/submit
④ GET   /documents/reviews/tasks         → 从这里提取 taskId ← 关键
⑤ POST  /documents/reviews/tasks/{{taskId}}/approve
⑥ POST  /rag/search                      → 验证已可被检索到
⑦ POST  /ai/chat                         → 验证能答出内容
    注意：taskId 不是发布接口返回的，必须从 ④ 的待办列表里取 —— 这是最容易写错的一步。
    小技巧：第 ⑥ 步刚跑完可能搜不到 —— 索引是异步建的。在第 ⑤ 和 ⑥ 之间加一个 3~5 秒的等待步骤，这个「等一等才搜到」的过程本身就是 Phase 3 的最佳教材。

  5. 按阶段分组管理接口

    建议目录结构直接对齐学习阶段，接口多了也不乱： 

    Knowledge Hub
├── 01 认证        login / refresh / me / logout
├── 02 文档        CRUD / upload-parse / publish / archive / save-draft
├── 03 审核        submit / current / history / tasks / approve / reject
├── 04 RBAC        users / roles / permissions / teams
├── 05 检索        /search  /rag/search
├── 06 问答        /ai/chat  /ai/chat/stream  /ai/sessions
└── 07 图谱        overview / search / nodes / edges
调试常见报错对照：
401 → token 缺失/过期，先跑登录接口刷新 accessToken 变量；
403 → 身份不对，换 admin 账号或检查 permissions；
400 且提示字段不允许 → 全局 ValidationPipe 开了 forbidNonWhitelisted，多传的字段会直接报错，删掉多余字段即可；
500 且与问答/图谱相关 → 多半是 OPENAI_API_KEY 没配。

跑之前要知道的三件事

  1. 先起环境：计划里的每一步都是真打 http://127.0.0.1:3000。后端没起时不会报「脚本错」，而是 Apipost 直接抛 connect ECONNREFUSED 127.0.0.1:3000 —— 看到这个就去 docker compose up -d + pnpm start:dev。
  2. 身份变量分开了：计划用 adminToken / userToken 分别存两种身份；C 章示例里的 accessToken 是单身份的简化写法。两者不冲突，但别在同一条链路里混用。
  3. 断言分级：纯后端逻辑（登录、权限、状态机）断言严格，不符即中断报错；依赖外部组件（ES / Neo4j / LLM）的步骤只告警不判失败，避免基础设施没配好就满屏红。
三处「接口文档与实现不一致」——照文档调必然 400，按 DTO 传才对：
① POST /documents/reviews/tasks/{{taskId}}/approve：body 字段是 reviewComment，不是 comment；
② POST /ai/chat：传 content，不是 query；
③ POST /documents：tags 传逗号分隔字符串，不是数组。
根因都是全局 ValidationPipe 开了 forbidNonWhitelisted —— 多一个字段、少一个字段都会直接 400。
与 D 章自检表配合使用：计划跑绿只说明「链路通了」，回答得出 D 章那道题才说明「你懂了」。 两者都过，这个阶段才算真正拿下 —— 建议把这个组合当作每天的收工标准。

D避坑清单与自检表

启动期必踩的坑

  • init.sql 只在数据卷第一次创建时执行。改表后要手动 docker exec -i knowledge_hub_postgres psql -U user -d knowledge_hub < init-scripts/postgresql/init.sql，或 down && rm -rf volumes/postgres && up -d 彻底重建。
  • 后端没有全局路由前缀，别自己加 /api。
  • 前端 .env 不入库，默认 VITE_API_BASE=/api 由代码兜底。
  • ES 首次启动需要本地构建镜像（装 IK 分词器），比其它容器慢。

理解上的坑

  • 「刚发布搜不到」是预期行为（索引最终一致）。
  • Postgres 与 Mongo 没有跨库事务，靠补偿删除保证最终一致。
  • 机器人答不上某个内部制度时，先确认那篇文档已发布且你对它可见。
  • ES 里 document_id 用 keyword 而非 long，是为了避免雪花 ID 在 JS 中丢精度。
  • MQ 消费失败只记日志，没有重试与死信队列，需手工重新投递。
