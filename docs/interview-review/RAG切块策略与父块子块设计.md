# RAG 知识库切块策略：从固定 Token 切块到父子分块架构

> 整理自 2026-11-09 关于 AI 知识库切块与向量化的讨论
> 适用范围：企业内部知识库、RAG 检索、向量库（Milvus / PGVector / ElasticSearch 等）

---

## 0. 一句话结论

**固定 chunk size + 固定 overlap（如 500 token、重叠 50）是最简单的 baseline，但会切碎语义、造成跨 chunk 逻辑断裂。**
问题根源是**不看句子、段落、章节等天然语义边界，只按 token 数字硬切**；overlap 只能缓解表面症状，不能根治——重叠太少丢上下文，重叠太多带来重复向量和召回噪声。

推荐演进路径：**边界感知切分（立刻改）→ 父子分层分块（生产必做）→ 语义切分 / GraphRAG（按需）**。

**术语对照**

| 术语 | 英文 | 含义 |
|---|---|---|
| 切块 | Chunk / Chunking | 把长文档拆成适合向量化和检索的小段 |
| 重叠 | Overlap | 相邻 chunk 之间重复保留的文本 |
| 向量化 | Embedding | 把文本编码成向量存入向量库 |
| 父块 | Parent Chunk | 保留完整语义单元，存原文，不向量化 |
| 子块 | Child Chunk | 从父块内部切出，向量化，用于召回 |

---

## 1. 固定 Token 切块到底会丢什么语义

典型翻车场景：一段逻辑是【定义 → 条件判断 → 结论】，刚好跨在 500 token 的分割点上。

- 结论单独成一块，条件在另一块；即使重叠 50 token，**关键关联语句很可能不在重叠区内**
- 长列表、表格、代码、公式、分层文档（合同、规范、教程）尤其严重
- overlap 只是"把上一块的尾部机械复制过来"，它**并不知道哪里是语义边界**

两个高频坑：

1. 切在从句中间、跨"段落标题 + 正文"、跨表格行；
2. 大 overlap 产生大量近似向量，召回时一堆重复块，LLM 反而更容易混淆和幻觉。

---

## 2. 方案分级：从低成本改造到高级架构

### 2.1 方案一：边界感知切块（最推荐先升级，成本低、收益大）

**不是固定 token 一刀切，而是"设最大上限，优先在天然语义断点切"。**

流程：

1. 先按文档原生分隔符预切：标题（`#`、`##`）、空行、句号、分号、Markdown 块结束、HTML 块结束；
2. 把小段逐段合并，直到**接近但不超过**设定的最大 token 上限（如 500）；
3. overlap 不再固定写死 50 token，改成**从上一块尾部按"完整句子/完整段落"回退取样**。

断点优先级：`\n\n`（段落） > `。` / `；`（句子） > `\n` > 空格 > 空。

优点：

- 每个 chunk 尽量是一个自闭合的小主题；
- overlap 是完整语义碎片，不是半截话；
- 兼容纯文本、Markdown，不用重构链路；
- 开源框架天然支持：LangChain `RecursiveCharacterTextSplitter`、LlamaIndex `SentenceSplitter` 本质属于此类。

> ⚠️ 常见误用：`RecursiveCharacterTextSplitter` 默认按**字符**计数而不是 token，必须显式绑定 token 计数器（如 `tiktoken`），否则 500 字符 ≠ 500 token。

### 2.2 方案二：语义聚类切分（Semantic Chunking）

核心：**用 embedding 相似度判断"哪里该切"，而不是用 token 数量。**

流程：

1. 先拆成极小基础片段（单句或短句，50~100 token）；
2. 计算相邻片段向量相似度；
3. 相似度低于阈值 → 在此切开；高于阈值 → 合并进同一 chunk；
4. 必须加硬上限：合并后不得超过最大 token（embedding 模型有输入窗口）。

代表实现：LlamaIndex `SemanticSplitterNodeParser`、LangChain 社区 Semantic Chunker。

| 优点 | 缺点 |
|---|---|
| 真正跟随主题变化切分，同话题合并、换话题断开 | 多一次 embedding 调用，成本高、速度慢 |
| 适合散文、长文章、非结构化长文本 | 阈值难调，不同文档风格阈值不一致 |
| — | 对密集规范、表格类文档稳定性一般 |
| — | 易产生超大块，必须配 token 上限兜底 |

### 2.3 方案三：父子分层分块（Hierarchical Chunking，工业界主流，强烈推荐）

解决"跨 chunk 语义长依赖"最强方案之一，是中型以上知识库的架构升级首选。

结构：

- **父块（2000~4000 token 上限，实际按章节切）**：保留完整章节与逻辑，**不向量化、不直接参与检索**，只存原文；
- **子块（300~600 token）**：从父块内部切出，做 embedding 入库，负责召回；
- 所有子块携带 `parent_id` 与章节路径元数据。

检索流程：

```
query → embedding → 召回 Top-K 子块
      → 按 parent_id 去重 → 取回完整父块原文
      → 父块全文（+ 命中子块高亮标记）+ query → 交给 LLM 生成答案
```

> 变种：可额外为父块生成摘要建索引（Summary Index / Multi-Index），摘要与子块双路召回再融合。

这一方案直接解决了核心痛点：**召回靠碎片子块做精准匹配，生成时给 LLM 完整上下文，跨子块逻辑不再断裂**。同时 overlap 需求可大幅降低，甚至接近取消。

### 2.4 方案四：结构化感知切块（规范、手册、合同、API 文档、表格）

不是纯散文的知识库必须走这条路：

- **Markdown**：识别标题层级，`##` 二级标题即天然分割点；块绑定标题路径（`# 安装 → ## 环境要求`）；
- **PDF / Word**：识别章节、表头、图注、列表，禁止跨表格切；
- **代码**：按函数、类切，不切在函数中间；
- **表格**：整表入同一块；若必须拆，**每个子块都要复制表头**，否则单行数据脱离表头无法理解。

**加分项（成本极低、效果显著）**：把标题/路径/元数据注入每个 chunk 正文头部，例如：

```
【章节：环境配置｜小节：内存参数】
……原文……
```

embedding 时一起编码，向量自带上下文归属信息，召回明显提升。固定切块方案也能直接叠加这一招。

### 2.5 方案五：GraphRAG / LightRAG（知识强关联场景）

不再只依赖连续文本 chunk：

- 先做实体与关系抽取，把文档拆成【实体 + 关系三元组】，同时保留原文片段作为证据；
- 检索时沿知识图关联召回相关实体周边的全部证据片段，而不只是文本向量相似。

适合：跨大量文档、跨段落多跳推理的知识库。
缺点：实现重、计算贵、维护复杂。**小知识库没必要上。**

---

## 3. 五种方案横向对比

| 方案 | 开发成本 | 速度 | 语义完整性 | 适用场景 |
|---|---|---|---|---|
| 固定 token + 固定 overlap | 极低 | 最快 | 差 | Demo、快速验证 |
| 递归边界切分（断点优先 + token 上限） | 低 | 快 | 中等 | **绝大多数业务知识库，首选升级** |
| 语义相似度切分 | 中 | 慢 | 较好 | 长文本、叙事类文档 |
| 父子分层分块 | 中高 | 中 | 很好 | **生产级 RAG，强烈推荐** |
| GraphRAG / LightRAG | 高 | 慢 | 最好 | 知识强关联、多文档推理 |

## 4. 工程落地路线（循序渐进，别一步上复杂架构）

### Step 1：立刻可改，零架构改动

- 弃用纯固定 token 硬切，换成 **递归 token 切分器（断点优先、token 上限兜底）**；
- 上限 400~450 token（对 512 窗口的 embedding 模型留余量）；
- overlap 改为**取若干完整前置句子**，而非固定 50 token 截断；
- 每个 chunk 前置注入标题/章节路径元数据。

### Step 2：业务稳定后升级父子分块

子块负责向量召回，父块提供完整章节上下文给 LLM。对"跨 chunk 语义断裂"是质变式改善，效果通常优于继续调切分规则。

### Step 3：强关联知识场景再考虑语义切分或 LightRAG

不要一上来就追求复杂图架构。

## 5. 父块与子块：切多少、按什么切（核心）

### 5.1 先理清职责（很多人搞反）

| | 父块 Parent Chunk | 子块 Child Chunk |
|---|---|---|
| 定位 | 证据容器 | 检索探针 |
| 是否向量化 | **否** | **是** |
| 用途 | 召回后喂给 LLM 看 | 与 query 算相似度 |
| 切分依据 | 天然语义单元（章节） | Embedding 窗口 + 检索友好 |
| 大小约束 | LLM 上下文窗口 | embedding 模型输入上限 |

**铁律：子块从父块内部切出，子块永远不能跨父块。**

### 5.2 父块：按什么切、切多大

**分割依据（优先级从高到低）：**

1. **文档原生结构（第一优先）**
   - Markdown：按一级/二级标题切，一个 `##` 章节 = 一个父块，三级标题留在块内；
   - PDF/Word 手册、规范、合同：按章节、条款、小节；"条款定义 + 约束 + 例外"不可拆散；
   - API 文档：一个接口（请求 / 参数 / 返回 / 示例）= 一个父块；
   - 教程：一个独立小节（目标 + 步骤 + 结果）= 一个父块；
   - 表格：**整张表必须在同一父块内，严禁跨父块。**

2. **LLM 上下文窗口兜底硬上限（第二约束）**

   父块最终是要塞给 LLM 的，过长会导致一次召回多个父块就爆窗口。

   经验值：父块上限 **800 ~ 3000 token**

   | 模型规模 | 上下文窗口 | 建议父块上限 |
   |---|---|---|
   | 7B 小模型 | 4k | 800 ~ 1200 token |
   | 14B / 32B | 8k ~ 16k | 1200 ~ 2000 token |
   | 长上下文模型 | 32k+ | 最多 2500 ~ 3000 token，不建议更大 |

   > 为什么不搞 5k+ 父块：召回 3 个父块就上万 token，prompt 臃肿、细节易丢、成本飙升。

3. **兜底规则**：单个原生章节超过父块上限时，在**章节内部找次级断点**（三级标题、空段落）拆成多个父块，而不是直接按句子硬切。

**❌ 禁止**：父块按固定 token 硬切；父块跨章节、跨完整逻辑单元。

示例（运维文档）：

```
## 磁盘告警处理          ← 父块起点
磁盘告警触发条件：xxx
排查步骤 1：xxx
排查步骤 2：xxx
处理方案：xxx
回滚条件：xxx
## 内存告警处理          ← 新父块起点
```

假设"磁盘告警处理"整段统计 1400 token，落在区间内 → 即为 1 个父块。

### 5.3 子块：按什么切、切多大

**分割依据：**

1. **Embedding 模型最大输入长度（硬红线，必须留余量）**

   | 模型 | 最大输入 | 推荐子块大小 |
   |---|---|---|
   | BGE-large / BGE-m3（512） | 512 token | **380 ~ 450 token** |
   | BGE-m3-1024 | 1024 token | 700 ~ 850 token |
   | text-embedding-3-small | 512 | 400 左右 |
   | text-embedding-3-large | 1024 | 750 左右 |

   > 原理：embedding 模型在窗口顶格输入时，末尾 token 表征质量会下滑，**务必留安全余量，不要顶满 512**。

2. **语义边界优先 + token 上限兜底**
   在**同一父块内部**递归切分：优先在段落、句号、分号处断开，接近上限即停止，不把一句话劈成两半。

3. **子块 overlap：只在父块内部生效**
   overlap 不是用来跨父块的，它是同一父块内相邻子块互相覆盖，防止某个逻辑正好落在两个子块的缝隙里。

   | 子块大小 | 推荐 overlap |
   |---|---|
   | 400 token | 40 ~ 60 token（约 10%） |
   | 750 token | 80 ~ 100 token |

4. **元数据继承**
   向量库只存：子块文本、embedding、`parent_id`、章节路径。
   召回后凭 `parent_id` 去原文库（PG / 对象存储 / Mongo）读取完整父块。

**❌ 禁止**：子块跨父块；子块超过 embedding 窗口；子块切在表格、代码或句子中间。

### 5.4 生产默认基线（中文知识库 + BGE-large 512）

| 维度 | 取值 |
|---|---|
| 父块切分 | 优先二级标题，上限 **1500 token** |
| 子块切分 | **400 token，overlap 50 token**，句子边界优先 |
| 一个父块下子块数 | **3 ~ 8 个**（超过 8 个说明父块太大，应提前拆） |
| 召回 | Top 8 子块 → 按 `parent_id` 去重 → 最多 3 个父块喂 LLM |

### 5.5 完整判定流程（可直接照写成代码分支）

```
1. 加载单篇原始文档
2. 解析文档结构，提取标题树
3. 按标题 / 章节切出候选父块单元
   for 每个候选章节单元:
       统计 token
       if token <= 父块上限(如 1500):
           → 直接成为 1 个父块，分配 parent_id
       else:
           在章节内找次级断点（三级标题、空行）拆成多个父块，每个都不得超上限
4. 对每一个父块，独立切子块：
   在父块内部递归语义切分，最大子块 token = 400，overlap = 50
   所有子块绑定这个父块的 parent_id
   子块向量化，写入向量库
5. 父块原文单独存储（PG / 对象存储 / Mongo 均可），不向量化
```

---

## 6. 召回策略怎么配合父子块

```
Top-K 子块召回（如 top 8）
  → 去重 parent_id，得到不重复的父块列表（通常剩 2~3 个）
  → 父块完整原文 + query → LLM
```

> 关键点：**必须按 parent_id 去重**。否则同一个父块内多个子块同时命中，会把相同章节重复喂给 LLM，既浪费 token 又容易诱发幻觉。

---

## 7. 特殊文档的差异化处理

| 文档类型 | 父块 | 子块 | 注意 |
|---|---|---|---|
| 代码文档 | 一个函数 / 类 | 函数内分段注释 + 代码 | 绝不切断函数 |
| 表格 | 整张表 | 【表头 + 前若干行】、【表头 + 后若干行】 | **表头在每个子块里都要复制** |
| 长叙事 / 论文 | 无结构，先按 1200 token 上限切父块 | 父块内部再切子块 | 这是降级方案 |
| 合同 / 规范 | 一个条款或一个完整逻辑单元 | 条款内部按句子切 | 定义、约束、例外不可分离 |
| 故障排查手册 | 一个完整故障处理流程 | 按排查步骤切 | 步骤前后强依赖，靠父块兜上下文 |

## 8. 配套易踩细节

1. **Embedding 窗口要与 chunk 匹配**
   BGE-large 支持 512 token，chunk 不要顶满 512，留余量；硬塞接近上限，向量质量会下降。

2. **Overlap 不是越大越好**
   边界切分做好后，overlap 可降到 10% 以内。很多人开到 20%~30%，导致大量重复向量，召回一堆冗余块，LLM 更容易混淆。

3. **什么时候不需要父子块**
   文档本身很短，章节普遍在 400 token 以内时，父块 = 子块，普通 RAG 足够，不必上这套架构。

4. **适合用父子块的信号**
   单章节 800 token 以上、逻辑长依赖、需要跨句推理（故障排查、合同条款、技术规范、API 文档）。

## 附录 A：可直接使用的切分配置（tiktoken 计数版）

```python
import tiktoken
from langchain.text_splitter import RecursiveCharacterTextSplitter

enc = tiktoken.get_encoding("cl100k_base")

def tiktoken_len(text: str) -> int:
    return len(enc.encode(text))

splitter = RecursiveCharacterTextSplitter(
    chunk_size=450,                # 最大 token 数
    chunk_overlap=50,
    length_function=tiktoken_len,  # 关键：按 token 计数，不是字符
    separators=[
        "\n\n",   # 段落优先
        "\n",
        "。",
        "；",
        ". ",
        " ",
        "",
    ],
)
```

> 注意：这是递归字符分割。若要做到"overlap 只取完整句子"，需二次封装：拿到切分结果后，向前回退到最近的句子边界，再截取 overlap 部分。
