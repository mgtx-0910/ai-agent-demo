# RAG 知识库越权问题分析与防护方案

> 核心问题：RAG 知识库中已经按权限条件做了过滤，为什么还会出现越权？如何防止？

---

## 一、核心结论

RAG 里**就算加了权限过滤，依然会越权**，根源分为两大类：

1. **检索阶段的权限漏了（最常见）**：拿到了不该拿的文档片段；
2. **生成/引用阶段的越权**：检索结果本身没问题，但大模型自己推理、脑补、拼接出了无权数据。

> 常见误区：认为"在向量库查询时带上 `where 权限条件` 就万事大吉"，这是最大的认知错误。

**`where` 条件过滤 ≠ 权限安全。** 它只是**性能层面的预筛选**，不是安全边界。

---

## 二、为什么已经加了权限过滤，还会越权？

### 1. 向量检索的过滤本身有漏洞（检索侧）

向量数据库的 `metadata 过滤（where 条件）` 依赖两件事：**入库时权限标签打对 + 查询时过滤条件写对**。这里的坑非常多：

| 问题 | 说明 |
|---|---|
| **标签漏打、打错** | 很多系统只给【整个文档】存权限，**拆分 chunk 时忘记把权限 metadata 同步到每一个分片**。结果：文档本身有权限，但其中某几个 chunk 没有权限标签 → where 过滤拦不住，直接被召回。 |
| **权限粒度不匹配** | 文档是"部门 A 可见"，但业务实际是"部门 A 里只有角色 admin 可见"；过滤只按部门过滤，没叠加角色。 |
| **多条件逻辑写错** | `or/and` 写反、空值、null、数组包含判断 bug。例如权限是数组 `["user_123", "dept_5"]`，但向量库的数组匹配语法理解错，导致过滤失效。 |
| **向量库过滤能力限制** | 部分轻量向量库对复杂权限表达式、多值、嵌套权限支持弱；过滤是**后过滤**而非前置过滤：先算向量相似度，再过滤，极端情况下过滤逻辑被绕过（少数库的 bug）。 |
| **继承权限、动态权限没有刷新** | 用户刚被移除某文档权限、部门调整了，但 chunk 的 metadata 还是旧的；向量库不会自动同步权限，缓存的分片权限信息过期。 |

### 2. 段落内夹带了其他主体的敏感信息（隐蔽越权，高频坑）

举例：

> 文档 A（用户 u1 可读）里面写了一句：`用户 u4 的合同编号：HT-999，金额 xxx`

权限过滤成功，只召回了 u1 有权看的文档 A；但是文档 A 的内容里**内嵌了 u4 的敏感数据**，u1 本来不应该看到 u4 的合同信息。

👉 **这种情况：where 过滤完全生效，但依然越权。**

向量过滤只能控制"整个分片能不能召回"，**不能理解分片内部哪些字段属于谁**。

### 3. 大模型生成阶段的"幻觉拼接越权"（RAG 特有，非常难查）

检索回来的片段全部都是当前用户有权限的文档，但是：

- 模型把多个有权分片里的信息，交叉拼接，推理出了一个**无权的结论**；
- 模型记住了之前上下文里的敏感信息（对话上下文缓存、历史轮次），本轮检索没召回，但模型自己输出；
- 模型从通用知识库/参数权重里，吐出了业务敏感数据（极少，但存在）。

**典型场景：**

> 分片 1：A 项目成本 100w（用户可读）
> 分片 2：B 项目成本 200w（用户可读）
> 但业务规则：**不允许用户看到 A+B 汇总后的总预算**
> 模型自动求和输出，属于业务层面的越权，向量过滤完全拦不住。

### 4. 旁路漏洞（很多人忽略）

- 检索后的后处理、rerank 重排阶段：rerank 接口、二次过滤逻辑被跳过；
- 引用溯源返回原始文档链接：chunk 过滤了，但返回的 source 链接指向了无权限的原文；
- 调试接口、向量库直接访问接口、后台管理接口没有独立鉴权；
- 权限判断只在 RAG 主链路做，导出、下载、API 批量查询没有复用同一套权限规则。

### 5. 权限模型本身设计缺陷

- 只做**资源级权限**（文档能不能看），没做**字段级、行级权限**；
- 权限是白名单，但存在默认开放（没有权限标记 = 所有人可见）的兜底逻辑；
- 匿名用户、游客、内部账号权限没有隔离。

## 三、分层防越权架构（生产可用，四层防护）

> **核心思路**：不要把权限只压在向量库 where 过滤这一层，要多层校验，失败快速拒绝。

### 第一层：入库阶段（源头治理，最重要）

**1. Chunk 级打权限元数据，而不是文档级**

每一个切片，都带上完整权限标签：

```json
{
  "doc_id": "xxx",
  "readable_users": ["u1"],
  "readable_depts": ["d1"],
  "readable_roles": ["admin"],
  "data_owner": "u1",
  "sensitivity": "internal",
  "expire_permission": "2026-12-01"
}
```

- ✅ 分片和权限绑定，分片新增/更新/删除同步更新向量库；
- ✅ 权限变更时，**增量更新向量库 metadata 或直接删除旧 chunk 重写**，不能等。

**2. 敏感字段识别 + 脱敏入库（解决"分片内夹带别人敏感信息"）**

- 用 NER / 规则识别：手机号、身份证、合同号、其他用户 ID、薪酬，入库前脱敏；
- 如果不能脱敏，就把这类敏感条目单独拆成独立 chunk，单独加严格权限。

### 第二层：检索前置 + 后置双重鉴权（不要只靠向量库 where）

流程：

```
用户请求 → 拿到用户身份（uid、dept、roles）→ 生成权限过滤条件
```

1. **传给向量库做 metadata 过滤**（第一层过滤，挡掉大部分）；
2. **拿到召回 chunk 列表之后，业务代码再做一轮二次校验**；
   > 向量库的过滤只是"查询参数"，是不可信的（版本 bug、语法差异、参数被篡改）；业务侧必须再循环校验每一个 chunk 的权限标签。
   > 二次校验不通过 → 直接丢弃这个 chunk，不送入 LLM。
3. **Rerank 阶段也要带上权限过滤**：rerank 不要把已经被业务鉴权拦截掉的分片重新捞回来。

> 最佳实践：权限逻辑写在**业务服务里**，而不是交给向量库黑盒。向量库只当辅助过滤。

### 第三层：Prompt 侧 + LLM 输出护栏（防幻觉拼接越权）

就算所有召回 chunk 都有权限，模型依然会乱组合，这一层是兜底：

**1. 系统 Prompt 强约束模板**

```
约束：
1. 你只能基于【提供的上下文片段】回答，不允许使用上下文以外的知识；
2. 禁止跨主体汇总、对比无权聚合的数据；
3. 如果上下文里存在不属于当前查询用户的隐私/敏感字段，禁止直接输出；
4. 无法回答时，统一回复"无相关权限或资料"，禁止猜测推理。
```

**2. 输出后敏感词/实体审查（内容安全过滤器）**

识别输出内容里的黑名单实体、敏感编号，命中直接拦截返回拒绝。

### 第四层：溯源、审计、告警（事后发现越权）

- 每一次 RAG 请求日志必须记录：uid、权限条件、召回 chunk 列表、输入 prompt、LLM 输出、是否命中权限拦截；
- 告警规则：
  - 用户短时间大量命中高密级文档；
  - **二次鉴权校验失败的 chunk 数量 > 0**（这是高危告警！说明向量过滤失效了）；
  - 模型输出触发敏感实体拦截。

## 四、常见踩坑对比表

| 现象 | 根因 | 修复方式 |
|---|---|---|
| 加了 where 还召回无权限 chunk | chunk 没有同步权限标签 / 向量库过滤语法错误 | 分片粒度打 metadata + 业务二次鉴权 |
| 召回 chunk 有权限，但里面有别人的敏感数据 | 只做文档级权限，无字段级隔离 | 入库脱敏、敏感信息单独分片 |
| 召回全部合法，但回答输出汇总后越权 | 模型自主推理聚合 | Prompt 约束 + 输出内容审查 |
| 权限改了还能查到旧数据 | 向量 metadata 没有同步刷新 | 权限变更触发 chunk 元数据更新 |
| 调试接口、导出接口越权 | 权限校验逻辑没有统一封装 | 抽公共鉴权中间件，所有入口复用 |

## 五、进阶方案：行级 / 多租户 RAG 权限模型

如果是多租户、企业内部知识库场景：

1. **简单隔离**：向量库独立 namespace / collection（租户隔离，从物理上分开，最简单，不会跨租户越权）；
2. **复杂共享知识库**：metadata 多维度标签 + 业务服务统一 RBAC / ABAC 鉴权，向量库仅作为性能优化的预过滤层。

> **重要原则**：向量库不负责安全决策，它只是一个检索工具；安全决策一定在你的应用服务代码里。

---

## 六、总结

`where 条件过滤 ≠ 权限安全`，它只是**性能层面的预筛选**，不是安全边界。

越权来自三处：

1. 分片 metadata 漏打、不同步 → 检索捞到不该捞的；
2. 分片内部夹带其他主体敏感信息 → 资源有权，但内容里面字段越权；
3. 模型自主推理、拼接、聚合 → 召回没问题，生成越权。

**防护标准（五层闭环）：**

```
入库打标 → 向量预过滤 → 业务代码二次鉴权丢弃非法 chunk → LLM 约束 + 输出审查 → 审计告警
```
