# 企业知识库技术选型说明
### ——从需求来源到八个组件的"非它不可"论证

> 整理时间：2026-11-09
> 对应项目：`knowledge-hub-backend`（NestJS 企业知识库后端）
> 阅读提示：第一章业务背景为**示例设定**（用于面试与汇报叙事）；第二章之后的技术结论与仓库代码、`README.md`、git 提交历史一一对应。

---

## 摘要（30 秒版）

1. **需求不是"我们要做个 AI"，而是三个业务问题撞在一起**：新人上手慢、大客户尽调过不了、竞品投标开始打"AI 知识库"。三件事被同一方案同时解决，需求才立得住。
2. **选型的真正输入是数据画像与访问画像**，不是技术排行榜。1.2 万份文档、15GB 正文、30 万块、10 QPS 这组数字，直接决定了"单机够用、不要集群、必须可降级"。
3. **一条贯穿原则：一种数据放在最擅长它的存储里**。ES / Neo4j 全是**可重建的派生数据**，权威数据只在 PG（元数据）与 Mongo（正文）。
4. **每个组件都要能回答"不选它会怎样"**，同时写下代价：无跨库事务、索引最终一致、MQ 无死信、解析依赖外部服务。
5. **最忌讳**把八个组件当"架构豪华"，却说不清去掉任意一个的具体后果——那说明它是抄来的，不是选出来的。

## 一、需求是怎么来的

### 1.1 背景设定

一家 120 人的垂直 SaaS 公司，做连锁门店运营管理系统（排班、巡店、稽核、报表），付费席位 3 万+。研发 45 人：后端 18、前端 15、测试 6、运维 3、算法 3；**没有专职 DBA，没有大数据团队**。

这组人数很关键——它决定了所有选型必须满足"**3.5 个人、3 个月交付，且没有专人伺候中间件**"。

### 1.2 三个触发点同时发生

| 触发点 | 具体事实 | 性质 |
|---|---|---|
| **客服数据先暴露问题** | 2025 Q2 工单分析：Top 50 高频问题里 **62% 的答案已在文档中**，但一线不去翻。客服新人培养 6 周、实施顾问 10 周，当年离职 4 人，直接影响续费 | 成本压力（可量化） |
| **大客户尽调不通过** | 两个年费百万级客户在续约尽调中要求：ISO 27001 年审材料、SOP 变更记录、**谁在何时看过哪份制度**。当时文档散在飞书、个人网盘、员工本地盘，法务说不清"最新版是哪个" | 合规压力（一票否决） |
| **竞品在投标里打"AI 知识库"** | Q3 两次丢单，复盘写着"客户问能不能直接问系统，而不是自己翻手册" | 商业压力 |

CTO 在 Q3 战略会上的原话：

> **把公司五年攒下的文档，变成可检索、可审计、可问答的资产；先内部用，成熟后做成产品能力。**

注意措辞差别：立项理由**不是**"我们要做一个 RAG 项目"，而是"三个业务问题被同一方案同时解决"。前者拿不到预算，后者才拿得到。

### 1.3 立项：把模糊诉求写成验收指标

| 业务诉求 | 量化验收指标 | 现状 |
|---|---|---|
| 新人上手慢 | 实施顾问独立接客户周期 10 周 → 6 周 | 10 周 |
| 找人靠问人 | 制度检索平均耗时 8 分钟 → 30 秒内 | 8 分钟 |
| 客服重复问题 | 工单一次解决率 68% → 80% | 68% |
| 合规审计 | 任一制度可查"当前版本 + 变更人 + 审核记录" | 不可查 |
| 权限不能出错 | 越级访问 = 0（公开 / 团队 / 私有三级） | — |

**约束条件比需求本身更决定选型**：3 个月 MVP、3.5 人力；无专职 DBA，不能引入需专人伺候的集群；团队只会 NestJS/TS；必须 `docker compose up` 一键起；基础设施 ≤ 3000 元/月。

## 二、需求拆解：数据画像决定选型

先量清数据形态和访问形态，再谈用什么。这一步通常决定 80% 的选型结论：

| 维度 | 实测 / 估算 | 对选型的直接结论 |
|---|---|---|
| 文档总量 | 5 年约 1.2 万份，年增 3000 份 | 不需要分布式，单机足够 |
| 单文件大小 | 平均 2~8MB，最大 200MB（扫描合同合集） | 上传上限 200MB；解析要允许长时间等待或异步 |
| 正文总量 | 8~15GB Markdown | 长文本必须与元数据表分开 |
| 切块规模 | 512/64 切法约 30 万块，1024 维向量 | 需要 kNN，但 30 万级单机 ES 足够 |
| 日活 | 内部 80 人 + 客户侧 200 人 | 检索峰值 5~10 QPS，问答 1~2 并发 |
| 写频率 | 每天发布 10~30 份 | 索引更新低频写，天然适合异步 |
| 一致性 | 元数据/审核/权限强一致；索引允许秒级延迟 | PG 要事务，ES/Neo4j 可最终一致 |

**跳过这张表的两种翻车**：选型过重（30 万块就上专用向量集群 + Kafka）；选型过轻（PG `LIKE` 做中文检索，分词和向量都没有）。

## 三、选型流程：三道筛选

**第一道，硬性门槛**：① 能 Docker 单机跑、有官方镜像；② 有成熟 Node/TS 客户端（团队只有 TS 能力）；③ 开源或托管、无商业 license；④ **挂了能降级**。
→ 淘汰 Elastic 商业版、需独立集群运维的向量库、必须自研 Java/Scala 的组件。

**第二道，两周 PoC（裁决环节）**：200 份真实文档（文本 PDF / 扫描 PDF / DOCX / PPTX / 带表格 XLSX）跑通「解析 → 切块 → embedding → 召回」，用 20 个真实客服问题测 Hit@5。
→ 本项目换 MinerU 的直接原因，就是 PoC 发现 `pdf-parse` 对扫描件失败率约 30%。

**第三道，写决策记录**：每个组件必须回答——**不选它会怎样 / 考虑过什么替代 / 代价是什么**。

## 四、逐组件"非要不可"论证

### 4.0 一览

| 组件 | 承载什么 | 不选它的具体后果 |
|---|---|---|
| PostgreSQL | 19 张表：元数据、审核流水、RBAC 六表、团队、分类、互动、通知、AI 会话 | 权限体系失去外键与事务，"角色删了关联还在"，审计过不了 |
| MongoDB | Markdown 正文 `document_content` | 长文本进 PG 的 TEXT，列表分页、缓存、备份同时被拖累 |
| Elasticsearch | `kh_chunk`（分块 + 1024 维向量）、`kh_document`（文档级全文） | 中文分词与 kNN 无法在同一索引、同一权限过滤下融合 |
| Neo4j | 文档 / 块 / 实体节点与关系 | "这个流程涉及谁"类多跳问题答不出，向量只能召回零散片段 |
| Redis | 激活 token、重置验证码、对话热窗口 | TTL 清理要自己写定时任务，高并发写同一行有锁竞争 |
| RustFS（S3） | MinerU 抽出的图片、原始文件 | 图片进 Mongo 撞 16MB 上限；本地盘则多实例失效 |
| RabbitMQ | 发布后的三路索引消息 | 发布接口同步等 embedding + LLM，必然超时 |
| MinerU | PDF / 图片 / Office → Markdown | 扫描件失败率 30%，表格版式丢，后面全链路垃圾进垃圾出 |

### 4.1 PostgreSQL：结构化 + 强一致的那一半

- **不选会怎样**：这些表的价值全在"多表条件分页 + 外键 + 事务"。权限变更、审核状态流转一旦跨文档库，就会出现脏数据，合规审计不通过。
- **考虑过**：MySQL；MongoDB 一把梭（否：跨集合无事务，RBAC 本质是关系型数据）。
- **代价**：无专职 DBA，表结构靠 `init.sql` + 手工迁移，已列为待改进项。

### 4.2 MongoDB：长正文，只做单点读

- **不选会怎样**：正文平均 300KB、最大数 MB。进 PG 的 `TEXT` 后，列表页分页每次都要碰大字段。而正文访问模式极单一：**按 `document_id` 单点读整篇，永不 join、永不按正文过滤**。
- **考虑过**：对象存储存正文（否：要按文档做版本与定位）；PG TOAST（否：混合负载）。
- **代价**：**第二个库，没有跨库事务**。所以代码是"先写 Mongo → 再写 PG → 失败补偿删 Mongo"（`src/document/document.service.ts`）。
- **反例提醒**：版本快照 `kh_document_version.content` 反而是 PG 的 `TEXT`。说明"长文本必须进 Mongo"不是铁律，是**按主路径读写频率做的取舍**。

### 4.3 Elasticsearch：关键词与向量必须在同一索引

- **不选会怎样**：中文检索必须 IK 分词（"加签""差旅"用标准分词器会被切碎）；同时要向量召回；还要文档级高亮。**三件事必须在同一份权限 filter 下完成**，否则跨系统拼结果、权限条件写两遍且易不一致。
- **考虑过**：
  - **pgvector**：compose 用的确实是 `pgvector/pgvector:pg16` 镜像，但 `init.sql` 没建扩展、代码里没有向量表——**没用**。原因是 PG 中文全文弱，最后会变成"PG 做向量 + 另一引擎做关键词"；ES 一个索引就能把 `ik_smart` 的 BM25 与 1024 维 kNN 一起做，再用 RRF 融合。
  - **Milvus / Qdrant**：30 万块、10 QPS，成本收益不成立，且不解决分词，等于再加一个组件。
- **代价**：索引**最终一致**，刚发布可能搜不到；ES 挂了靠 `ELASTICSEARCH_ENABLED` 降级。所以它是**可重建的派生数据**，不是权威存储。
- **具体的坑**：`document_id` 必须映射 `keyword` 而非 `long`——雪花 ID 超出 JS 安全整数范围，用 `long` 会丢尾数导致串文档。镜像由 `elasticsearch/Dockerfile` 本地构建，因为官方镜像不含 IK。

### 4.4 Neo4j：V2 才加，且只解释关系

- **需求来源**：上线后发现"这个客户要走哪些审批环节""张敏负责的流程和谁对接"答不好——答案不在某段文字里，而在**实体之间的关系**上。
- **不选会怎样**：PG 存三元组要递归 CTE，两跳以上性能与可读性都崩；ES 只能做单跳过滤。
- **产品约束**：**图谱只用于解释关系，不能当制度原文**，这句写进了工具描述和 system prompt，避免模型把关系编成不存在的制度。
- **代价**：抽取依赖 LLM，未配 Key 该管线直接失败，所以有独立开关 `NEO4J_ENABLED`。

### 4.5 Redis：只放一次性与热数据

- **不选会怎样**：验证码过期要靠定时任务清理，高并发写同一行有锁竞争；`SETEX` 一行解决。
- **边界**：**只做缓存，不做权威存储**。对话历史永远在 PG，key 过期从 PG 回填（`chat-short-memory.service.ts`），Redis 清空不丢历史。

### 4.6 RustFS：二进制不进数据库

- **不选会怎样**：图片进 Mongo 撞 16MB 单文档上限；进本地盘则多实例部署要共享盘。
- **真正的价值在 S3 协议**：标准 SDK，换 OSS / MinIO / AWS 只改 endpoint。
- **代价**：解析含图时必须启用（`RUSTFS_ENABLED=true`），否则直接报错而不是返回失效路径——刻意的失败策略。

### 4.7 RabbitMQ：发布是轻动作，索引是慢动作

- **不选会怎样**：发布要做「清旧块 → 切块 → embedding → 写 ES → LLM 抽实体写 Neo4j」。embedding 每批几百毫秒、LLM 几秒到几十秒，同步做必然超时；定时扫表则延迟不可控、易重复处理。
- **为什么三条队列**：三种索引耗时差一个数量级、失败原因不同，拆开后**一个失败不影响另外两个**，也能单独关闭某一路。
- **刻意的设计**：Search 消息**只带 `documentId`，不带正文**，消费者回查 Mongo；否则 MQ 里跑 GB 级文本。
- **代价**：无重试与死信队列，失败只记日志（已列为限制），是 3 个月人力的妥协。

### 4.8 MinerU：解析质量是第一道关口

- **不选会怎样**：PoC 里 `pdf-parse` 对**扫描版 PDF 失败率约 30%**；PPTX/XLSX 的表格与版式还原不出来，而"门店配置手册""稽核评分表"主体恰恰是表格。解析不准，embedding 与 LLM 全部白做。
- **链路**：申请上传链接 → PUT 到签名 URL（不能带 `Content-Type`）→ 轮询（3s 一次，超时 600s）→ 下载 zip 取 `full.md`，图片传 RustFS → 清洗后写 Mongo。
- **代价**：强依赖外部 API 与额度，同步轮询最长 10 分钟，大文件会让请求长期挂起，后续应改 MQ 异步解析。第一代本地解析器保留作降级参考。

## 五、跨组件的关键决策

### 5.1 三套索引 = 同一份正文的三种投影

权威数据只有 PG + Mongo，ES / Neo4j 全部可重建。由此得到三条：索引服务挂了可降级（`ELASTICSEARCH_ENABLED` / `NEO4J_ENABLED`）；改可见性只更新 `is_public` / `team_id`，**不重跑 embedding 与实体抽取**；重建前 `deleteByDocId` 清旧块，重复发布不产生脏数据。

### 5.2 权限规则只写一次，再下推到三个存储

规则集中在 `src/document/document-access.ts`：

```
可读 = 管理员/审核员（unrestricted）
     OR 文档作者是自己
     OR （已发布 AND（文档公开 OR 文档 team_id IN 我的团队集合））
```

| 存储 | 下推方式 |
|---|---|
| Postgres | QueryBuilder 拼可见性条件 |
| Elasticsearch | `esVisibilityFilter()` → `bool.should + minimum_should_match:1`；`wrapEsQuery()` **相关性放 must、权限放 filter**，权限不影响打分 |
| Neo4j | `neo4jDocumentAccessWhere()` 生成 Cypher + 参数化传值 |

做不对，检索就是越权入口——比"召回不准"严重得多。

### 5.3 没有跨库事务，就把不确定性面积压到最小

强一致部分（状态流转、审核结论、权限）全在 PG 单库事务内；跨库只有"正文"一件事，用补偿删除兜底；补偿本身失败写进已知限制，需人工介入。

### 5.4 所有外部依赖都有开关

| 故障 | 行为 |
|---|---|
| 未配 Embedding Key | 本地哈希向量 |
| 向量化失败 | 退化为纯关键词检索 |
| Rerank 不可用 | 直接返回 RRF 顺序 |
| 未配 Mem0 / Bocha | 整体跳过，不影响主链路 |

## 六、评审会上的三个尖锐问题

**Q1：一个小系统为什么 5 个存储 + 1 个 MQ？**

A：每个对应一种**完全不同的访问模式**：强一致关系型 / 长文本单点读 / 全文+向量 / 多跳关系 / 短 TTL / 二进制。合并的代价不是"省一个组件"，而是某类数据的查询变差或事务缺失。但也承认：V1 只有 PG + Mongo + ES + Redis + MQ，Neo4j 是 V2 加的，对象存储是解析图片才必须的。只能留三个就留 PG、ES、对象存储。

**Q2：为什么不上 Milvus / Kafka / K8s？**

A：量级不够。30 万块、10 QPS，ES 单机够用；Kafka 的吞吐优势在这里是负收益。**架构匹配团队规模与业务量级，不匹配技术排行榜。**

**Q3：没有跨库事务，不一致怎么办？**

A：接受最终一致 + 补偿兜底，并把"补偿失败需人工"写进限制。强一致部分全收在 PG 单库，跨库只有正文一件事——压小不确定性，而不是幻想消除它。

## 七、分期落地

| 阶段 | 周期 | 内容 | 选型动作 |
|---|---|---|---|
| V1 | 6 周 | 上传 + 解析 + 发布审核 + 关键词/向量检索 + 问答 | PG / Mongo / ES / Redis / RabbitMQ |
| V1.1 | 4 周 | 换 MinerU（救回扫描件）、补对象存储 | RustFS |
| V2 | 6 周 | 图谱问答、权限下推三套索引、评测集 | Neo4j + `pnpm eval:rag` |
| V3 | 持续 | 可见性变更不重跑 embedding、降级开关、Langfuse | 可观测性 |

分期标准是**业务验收指标**：能答对问题 > 图谱好看。图谱是"答不好的那类问题"倒逼出来的，不是第一天规划的。

`git log -- knowledge-hub-backend` 显示选型是**增量长出来的**：

```

5c7a08f  文件上传解析为 Markdown + RustFS 对象存储

f4123c5  KG 知识图谱管线（LLM 抽取 → Neo4j）
ffe1b5b  文档发布审核流程与文档状态机
a3aa0cf  账号权限体系与 AI 问答
```

## 九、常见误区

| 误区 | 为什么不对 |
|---|---|
| "文档不多，一个 PG 全搞定" | 元数据、长正文、检索索引是三种访问模式；合并后分页、备份、召回率同时变差 |
| "用了向量就得上专用向量库" | 30 万块、10 QPS，单机 ES 的 kNN 足够；专用库还丢掉关键词与分词 |
| "ES 能搜，正文也放 ES" | ES 是派生索引、随时可重建，当权威存储会失去事务与更新语义 |
| "MQ 换成定时扫表" | 延迟不可控、易重复处理、无法按索引类型独立失败 |
| "解析随便找个 pdf 库" | 解析错一个字，embedding 与 LLM 全部白做；扫描件和表格是这类系统的主体 |
| "先 top-k 召回再按权限过滤" | 无关/恶意内容已占用召回名额，正确做法是**元数据前置过滤** |
| "多数据库就是炫技" | 判断标准只有一个：能否说清去掉它之后**具体哪一步会坏** |
| "架构一次设计到位" | Neo4j、MinerU、Langfuse 都是后续被真实问题逼出来的 |

## 附录 A：术语注解表

| 术语 | 解释 | 在本项目中的位置 |
|---|---|---|
| **元数据（Metadata）** | 描述文档的结构化字段：标题、状态、作者、团队、分类、计数 | PG 的 `kh_document` 等 19 张表 |
| **正文（Body）** | 解析后的 Markdown 全文 | Mongo `document_content` |
| **派生数据（Derived Data）** | 由权威数据计算得来、可随时重建的数据 | ES 两个索引、Neo4j 图谱 |
| **最终一致（Eventual Consistency）** | 写入后短时间内外可见状态不同，最终收敛 | 发布后索引延迟可见 |
| **补偿事务（Compensating Transaction）** | 跨库写入失败后，用反向操作撤销已成功的部分 | 先写 Mongo → 写 PG 失败 → 删 Mongo |
| **IK 分词器** | 中文分词插件，`ik_max_word` 建索引、`ik_smart` 检索 | 烤进 ES 镜像 |
| **dense_vector / kNN** | 稠密向量字段与最近邻检索 | `kh_chunk.embedding`（1024 维，cosine） |
| **BM25** | 关键词相关性打分算法（倒排索引） | `kh_chunk` 的关键词路 |
| **RRF（Reciprocal Rank Fusion）** | 按排名倒数加权融合多路召回结果，无需分数归一化 | 关键词 + 向量两路融合，`RAG_RRF_C=60` |
| **Rerank** | 召回后的精排模型，精度高但慢 | `qwen3-rerank`，阈值 0.4 |
| **Chunk / Overlap** | 分块与相邻块重叠，避免语义被切断 | 512 / 64 |
| **ACL 下推** | 把权限条件写进各存储的查询语句，而不是查完再过滤 | `document-access.ts` 三套构造器 |
| **雪花 ID 精度问题** | 64 位 ID 超出 JS `Number.MAX_SAFE_INTEGER`，用 `long` 会丢尾数 | ES 用 `keyword` 存 `document_id` |
| **死信队列（DLQ）** | 消费失败多次后转入的兜底队列 | 本项目**未实现**，已列为限制 |
| **S3 兼容** | 遵循 AWS S3 API 的对象存储，SDK 可互换 | RustFS |
| **OCR** | 图片/扫描件文字识别 | MinerU 对图片与扫描 PDF 自动开启 |
| **降级开关** | 用环境变量关闭非核心依赖，避免全站不可用 | `ELASTICSEARCH_ENABLED` 等 |

## 附录 B：选型评审自查清单

**需求与量级**
- [ ] 能否用一句话说清"不做这个会损失什么"（成本/合规/收入）？
- [ ] 验收指标是否量化（周期、耗时、解决率、越权数）？
- [ ] 数据量与 QPS 是否实测过，而不是拍脑袋？

**每个组件**
- [ ] 去掉它之后，**具体哪一步**会坏？
- [ ] 考虑过哪些替代方案，否掉的理由是什么？
- [ ] 它的代价写进文档了吗（一致性、运维、费用、外部依赖）？

**数据边界**
- [ ] 哪些是权威数据，哪些是可重建的派生数据？
- [ ] 跨库写入失败时，补偿逻辑是什么？补偿失败怎么办？
- [ ] 权限条件是否下推到每个存储，而不是查完再过滤？

**工程可行性**
- [ ] 3 个人能不能维护？有没有专职运维？
- [ ] 能否 `docker compose up` 一键复现？
- [ ] 每个非核心依赖都有降级开关吗？

## 附：一句话记住这套方案

> **先从业务痛点拆出四类数据（结构化元数据 / 长文本 / 检索索引 / 关系），按访问模式各归其位；把耗时的索引构建抽成异步队列；把所有外部依赖做成可降级开关；最后把每个选择连同它的代价一起写进文档——能说清"不选会怎样"，才叫选型。**
