# 大模型基础：Transformer 图解笔记

> 本篇是 **24 张原理图**的串讲笔记，图源目录：`docs/agent-imgs/transformer-img/`。
> 它不在三份阶段总结里——三份总结讲的是「怎么用 LangChain 把大模型接进系统」，这一篇补的是「大模型本身是怎么工作的」。
>
> 一条主线先记住：
>
> **文本 → token → 向量 → 注意力加权融合 → FFN → 输出投影 → softmax → 采样出下一个 token → 拼回输入再来一遍（自回归）**
>
> 训练阶段反复跑这条前向链路并反向传播改参数；推理阶段只跑前向、不改参数，靠 KV 缓存加速。

---

## 0. 一张图看懂全貌

### 0.1 Transformer 架构与大模型总结图

![Transformer 架构与大模型总结图](<agent-imgs/transformer-img/Transformer 架构与大模型总结图.png>)

看这张图时只抓三层：

| 层次 | 里面有什么 | 作用 |
|---|---|---|
| 输入侧 | token 化 + 位置编码 + Embedding | 把文字变成带顺序信息的向量 |
| 主干 | 多头自注意力 + 前馈网络（FFN）+ 残差 & LayerNorm | 让每个 token 参考其它 token 来更新自己的表示 |
| 输出侧 | 输出投影 + Softmax | 把最后一层向量映射成「词表里每个词的概率」 |

大模型的「大」主要指主干被堆叠的层数、注意力头数和隐藏维度——结构没变，规模变了。

### 0.2 两大 Transformer 架构分工明确，共同支撑 AI Agent 的完整能力

![两大Transformer架构分工明确，共同支撑AIAgent的完整能力](<agent-imgs/transformer-img/两大Transformer架构分工明确，共同支撑AIAgent的完整能力.png>)

- **Encoder 系**（双向注意力）：擅长「理解整段文本」，代表用途是**向量化/检索**（embedding）、分类、重排（rerank）；
- **Decoder 系**（单向掩码注意力）：擅长「往后接着写」，代表用途是**生成**（对话、写代码、抽实体、造答案）。

回到本项目：`kh_chunk` 的 1024 维向量、`qwen3-rerank` 精排属于 Encoder 系能力；`createAgent` 里的问答、查询改写、图谱实体抽取属于 Decoder 系能力。**混合检索 + Agentic RAG 其实就是两类模型分工的结果**。

## 1. 输入：文本先被拆成 token

### 1.1 Transformer 输入文本拆分为 Token 的原理

![Transformer 输入文本拆分为Token的原理](<agent-imgs/transformer-img/Transformer 输入文本拆分为Token的原理.png>)

模型不认识「字」或「词」，只认识词表里的 **token id**。分词器（BPE 之类）把文本切成子词，再查表转成整数 id，最后经 Embedding 矩阵变成向量。

工程上的直接后果：

- **计费与上下文长度都是按 token 算**，不是按字数——中文大致 1 字 ≈ 1 token，英文常见词可能 1 个 token 覆盖多个字符；
- **同一个词在不同上下文里可能被切成不同 token**，所以「数字运算、罕见专有名词」容易出错；
- 分块策略里的 `512/64`（512 token 一块、64 重叠）就是按 token 计的，不是按字符。

### 1.2 给模型所有已知的信息示例

![给模型所有已知的信息示例](<agent-imgs/transformer-img/给模型所有已知的信息示例.png>)

这张图回答一个最常见的问题：**为什么大模型看起来「什么都知道」？**

因为它只在做一件事——**给定前面所有已知的 token，预测下一个 token 的概率分布**。所谓「知道」，是把训练语料里学到的搭配规律，在推理时按上下文约束重新算了一遍概率。

由此推出 RAG 存在的意义：模型参数里的知识**不可控、会过时、无法追溯出处**；把制度原文塞进上下文（检索 + 引用）才是「有据可依」的做法。

## 2. 注意力：Q、K、V 到底是什么

### 2.1 Transformer 中的 Q、K、V 是什么

![Transformer 中的 Q、K、V 是什么](<agent-imgs/transformer-img/Transformer 中的 Q、K、V 是什么.png>)

用一句话记：**Query 是「我在问什么」，Key 是「我能提供什么标签」，Value 是「我真正携带的内容」**。

计算过程：

```
Attention(Q, K, V) = softmax( Q·Kᵀ / √d_k ) · V
                     └── 相关性打分 ──┘   └ 加权求和 ┘
```

1. 每个 token 用自己的向量分别乘三组权重矩阵 Wq / Wk / Wv，得到 Q、K、V；
2. Q 和所有 K 做点积 → 得到「我该关注谁」的分数，除以 √d_k 防止数值过大、softmax 饱和；
3. softmax 归一化成权重，再对 V 加权求和，得到这个 token 的新表示。

**多头注意力**就是并行做若干组，让模型同时关注语法关系、指代关系、语义相似等不同侧面。

### 2.2 双向注意力 vs 单向掩码注意力

![双向注意力vs单向掩码注意力(生成任务对比)](<agent-imgs/transformer-img/双向注意力vs单向掩码注意力(生成任务对比).png>)

| | 双向注意力 | 单向掩码注意力 |
|---|---|---|
| 能否看到后面的 token | 能 | 不能（未来位置被 mask 成 -∞） |
| 典型任务 | 理解：embedding、分类、rerank | 生成：对话、续写 |
| 训练目标 | 完形填空式（遮住中间猜中间） | 下一 token 预测 |
| 本项目对应 | `kh_chunk` 向量、qwen3-rerank | `/ai/chat` 的问答与改写 |

这里有一个容易混的点：**encoder-only 模型不能拿来生成，decoder-only 模型不做检索**——它们是两套分工，不是谁替代谁。

### 2.3 Encoder 与 Decoder 示例

![Encoder与Decoder示例](<agent-imgs/transformer-img/Encoder与Decoder示例.png>)

经典的 Encoder-Decoder（如翻译模型）：Encoder 先双向读完整句，Decoder 再单向逐字产出，Decoder 中间有一层 **Cross-Attention**，用「自己产生的 Query」去查「Encoder 输出的 Key/Value」。

理解这一点的价值：**它就是「检索增强」的原始形态**——生成时去查外部表示。RAG 只是把 Encoder 换成了 ES 检索、把 Key/Value 换成了文档块。

## 3. 一次前向：从 QKV 到下一个 token 的概率

### 3.1 QKV 加权融合后的向量送入 FFN

![QKV加权融合后的向量送入FFN](<agent-imgs/transformer-img/QKV加权融合后的向量送入FFN.png>)

注意力解决的是「** token 之间怎么交换信息**」，但它本质是加权平均，表达能力有限；所以每个 Transformer 块在注意力之后接一个 **前馈网络 FFN**（两层线性 + 激活，中间维度通常放大 4 倍左右）：

```
x → LayerNorm → Multi-Head Attention → 残差相加
  → LayerNorm → FFN（升维 → 激活 → 降维）→ 残差相加
```

分工可以这样记：**注意力负责「横向找谁相关」，FFN 负责「纵向做非线性加工」**。模型参数量里 FFN 往往占大头。

### 3.2 输出投影与 Softmax

![输出投影与Softmax](<agent-imgs/transformer-img/输出投影与Softmax.png>)

最后一层出来的还是「隐藏维度」的向量（比如 4096 维），要经过**输出投影矩阵**映射到**词表大小**（比如 15 万维），再过 softmax 变成概率分布。

关键点：

- 投影矩阵输出的是 **logits（未归一化分数）**，softmax 之后才是概率；
- 词表有多大，这一步就有多少维——**大词表是显存与计算开销的一大来源**；
- 训练时用 softmax + 交叉熵直接对齐「正确答案 token」，这就是下一节要讲的损失。

### 3.3 从 FFN 之后到下一个 token 的流程

![从FFN之后到下一个token的流程](<agent-imgs/transformer-img/从FFN之后到下一个token的流程.jpg>)

把上面两步连起来，一次「说一个 token」的完整动作是：

```
最后一层隐藏状态（取最后一个位置的向量）
   → 输出投影（hidden → vocab）
   → softmax（得到整个词表的概率分布）
   → 采样（贪心 / 温度 / top-p / top-k）
   → 得到下一个 token
   → 把它拼回输入序列，回到第 1 步
```

注意最后一步：**生成的 token 会被喂回输入**，这就是自回归的循环结构。

## 4. 自回归：模型是怎么「一个字一个字说」的

### 4.1 自回归生成（Autoregressive Generation）的含义

![自回归生成(Autoregressive Generation)的含义](<agent-imgs/transformer-img/自回归生成(Autoregressive Generation)的含义.png>)

自回归 = **把上一次的输出当作下一次的输入**。所以：

- 输出是**逐 token 流式产生**的，不是整体一次成形——这正是本项目 `/ai/chat/stream` 能把「思考过程 + 正文」一段段推给前端的前提；
- 中间任一步采样错，后面会基于错误内容继续往下写（幻觉会自我一致地扩散）；
- 「首 token 延迟」和「输出速度（token/s）」是两个独立指标，用户体验主要受后者影响。

### 4.2 自回归生成过程与 QKV 的关系（通俗例子）

![自回归生成过程与QKV的关系(通俗例子)](<agent-imgs/transformer-img/自回归生成过程与QKV的关系(通俗例子).jpg>)

每一步生成时：

- **当前要预测的那个位置产生 Query**；
- 它前面所有位置的向量充当 Key / Value（被反复复用）；
- 因此「前面那些 token 的 K/V 只要算过一次就不会变」——这直接引出下一节的 KV 缓存。

### 4.3 transformer 推理示例

![transformer推理示例](<agent-imgs/transformer-img/transformer推理示例.png>)

用一句「小猫咪坐在」推「垫子上」这类例子走一遍：输入先过 Embedding，再逐层过注意力与 FFN，最后在末位得到「下一个 token 的概率分布」，取概率最高的那个。

### 4.4 完整的推理

![完整的推理](<agent-imgs/transformer-img/完整的推理.png>)

这张图把「输入 token → 逐层计算 → 输出分布 → 采样 → 回填 → 再算」的整条推理链路收在一起。理解它的意义在于：**你能看出哪些环节可以优化**——

| 环节 | 常见优化 |
|---|---|
| 逐 token 重复计算 | KV 缓存、连续批处理（continuous batching） |
| 注意力 O(n²) | FlashAttention、GQA/MQA |
| 权重太大放不下 | 量化（INT8/INT4）、张量并行 |

## 5. KV 缓存：为什么第二轮开始变快

![KV缓存](<agent-imgs/transformer-img/KV缓存.jpg>)

没有缓存时，每生成一个 token 都要**把前面所有 token 重算一遍**，总计算量随长度近似平方增长。KV 缓存把每层已经算好的 Key / Value 存起来，新 token 只需要：

1. 算自己的 Q / K / V；
2. 把新 K、V 追加进缓存；
3. 用自己的 Q 去查**全部** K（含缓存的历史）。

于是单步计算量从「全长重算」降为「只算新增位置」，这就是对话越长越明显的那份加速。

代价也很实际，值得在面试里主动提：

- 缓存占用 **≈ 2 × 层数 × 头数 × 维度 × 序列长度 × 精度字节**，长上下文时显存被 KV 吃掉；
- **它只对同一条前缀有效**：上下文一变（比如 RAG 每轮重新拼不同的检索结果），前缀不同，缓存基本失效；
- 服务端多轮对话要按 session 隔离并设置过期——和本项目里 Redis 短期记忆「最近 20 条、带 TTL」是同一类工程约束。

## 6. 训练阶段：参数是怎么学出来的

### 6.1 大模型训练阶段流程图（通俗易懂版）

![大模型训练阶段流程图(通俗易懂版)](<agent-imgs/transformer-img/大模型训练阶段流程图(通俗易懂版).png>)

训练循环四步，反复迭代：

```
前向传播（预测下一个 token 的概率分布）
   → 计算损失（和真实的下一个 token 比，差多少）
   → 反向传播（求每个参数对损失的梯度）
   → 优化器更新参数（按梯度反方向调一小步）
```

再叠加预训练 → 指令微调（SFT）→ 对齐（RLHF/偏好优化）的阶段划分：**预训练学「语言与世界」，微调学「听指令」，对齐学「怎么说更合适」**。

### 6.2 训练阶段 学习词的搭配规律（下一词预测）

![训练阶段 学习词的搭配规律(下一词预测)](<agent-imgs/transformer-img/训练阶段 学习词的搭配规律(下一词预测).jpg>)

千亿参数不是被人逐条写规则写进去的，而是从「预测下一个词」这个**自监督任务**里被逼出来的统计规律。

这也解释了两件事：

- 为什么大模型**特别擅长模仿风格、特别不擅长精确计算与事实核验**——它优化的是「像不像下一个词」，不是「对不对」；
- 为什么**标注数据质量决定微调效果**：同一个目标函数下，喂什么就学什么。

### 6.3 计算损失、反向传播是什么意思

![大模型训练阶段 计算损失、反向传播是什么意思](<agent-imgs/transformer-img/大模型训练阶段 计算损失、反向传播是什么意思.jpg>)

- **损失（loss）**：真实 token 的预测概率取负对数——预测得越自信且正确，损失越小；
- **反向传播**：从损失出发，用链式法则逐层往回求每个参数的梯度；
- **梯度下降**：沿梯度反方向更新参数，学习率决定步子大小。

面试里常被追问的一点：**推理阶段不做反向传播、也不改参数**。模型一旦「出厂」，它的知识就冻结了——所以想把项目里的新文档变成模型能力，要么微调（改参数）、要么 RAG（改上下文）。**我们选 RAG，因为它是可更新、可追溯、可权限控制的那条路**。

### 6.4 为什么 AI 训练要在显卡（GPU）上跑

![为什么AI训练要在显卡(GPU)上跑](<agent-imgs/transformer-img/为什么AI训练要在显卡(GPU)上跑.png>)

训练的主力运算几乎全是**大规模矩阵乘法**，天然可并行：

| | CPU | GPU |
|---|---|---|
| 核心数 | 少（几十） | 多（上千至数万） |
| 单核能力 | 强、擅长复杂控制流 | 弱、但吞吐极高 |
| 显存/内存带宽 | 相对小 | 带宽大，适合喂满算力 |

所以 CPU 适合调度与推理小模型，GPU 适合并行张量计算。**推理同样吃显存**：权重 + KV 缓存 + 激活值——这也是小模型能跑在 CPU、长上下文大模型必须上卡的直接原因。

## 7. 训练 vs 推理：同一个模型的两副面孔

### 7.1 自回归语言模型的工作流程：训练阶段 vs 推理阶段

![自回归语言模型的工作流程 训练阶段vs推理阶段](<agent-imgs/transformer-img/自回归语言模型的工作流程 训练阶段vs推理阶段.png>)

| | 训练阶段 | 推理阶段 |
|---|---|---|
| 输入 | 完整句子的全部 token（并做掩码） | 已知前缀 |
| 输出 | 每个位置的下一个 token 分布 | 只需**最后一个位置**的分布 |
| 是否更新参数 | 是（反向传播 + 优化器） | 否（参数冻结） |
| 并行度 | 位置维度可并行（teacher forcing） | 逐 token 串行 |
| 显存瓶颈 | 激活值 + 优化器状态 + 梯度 | 权重 + KV 缓存 |

**训练可以并行、推理必须串行**，这一条差异解释了很多工程现象：为什么训练要几千卡几周，而推理优化全部围绕「单步延迟」和「显存占用」。

### 7.2 大模型出厂与推理阶段

![大模型出厂与推理阶段](<agent-imgs/transformer-img/大模型出厂与推理阶段.png>)

「出厂」之后模型是只读的：同一份权重可以同时服务无数请求，因此**服务端能做缓存、能批处理、能横向扩容**；而要让模型「知道新东西」，只能在**上下文层**做文章（RAG、记忆、提示词）或在**参数层**再训练（微调）。

本项目的选择很清楚：**知识进上下文，不进参数**。

### 7.3 大模型训练与推理总结

![大模型训练与推理总结](<agent-imgs/transformer-img/大模型训练与推理总结.jpg>)

把两部分合起来记一句话：

> **训练 = 前向 + 反向 + 更新，目标是让「预测下一个 token」更准；推理 = 只做前向 + 采样，目标是用更少的显存和更低的延迟产生可用的下一个 token。**

## 8. 采样：同样的概率分布，为什么每次回答不一样

![各种采样策略和温度的区别](<agent-imgs/transformer-img/各种采样策略和温度的区别.jpg>)

拿到概率分布后，怎么挑词决定了输出风格：

| 策略 | 做法 | 效果 |
|---|---|---|
| 贪心（greedy） | 直接取概率最高的 | 稳定但呆板、易重复 |
| 温度 T | logits 除以 T 再 softmax：T<1 更尖（更确定），T>1 更平（更发散） | 最常用的旋钮 |
| top-k | 只在概率最高的 k 个里采样 | 砍掉长尾，防乱说 |
| top-p（核采样） | 取累计概率达 p 的最小集合再采样 | 比 top-k 自适应，更主流 |

工程对应关系：

- 要**结构化输出、抽取实体、生成查询词** → 低温（≈0~0.2），保证可复现；
- 要**写文案、头脑风暴** → 高温（≈0.7~1.0）；
- 温度 0 也不是绝对确定（硬件与批处理会带来微小数值差异），所以**「同样的提示词必然得到同样答案」是不成立的**——评估与回归测试要按此设计。

## 9. 一个生活化类比

![生活场景例子 妈妈教我做早餐](<agent-imgs/transformer-img/生活场景例子 妈妈教我做早餐.jpg>)

这张图把训练与推理类比成「妈妈教做早餐」：

- **训练** = 孩子做完、妈妈指出哪里不对（损失），孩子下次调整（更新参数）；
- **推理** = 孩子独自下厨，按学到的习惯一步步做（只做前向）；
- **自回归** = 一步做完才有下一步，第一步炒糊了后面全歪；
- **上下文（RAG）** = 今天冰箱里有什么、家里人忌口什么——**不改变孩子的手艺，只改变这次做什么**。

这是给非技术听众讲「微调 vs RAG」时最好用的一段类比。

## 10. 回到 AI Agent：这套原理怎么落到本项目

| 原理 | 在本项目里的体现 |
|---|---|
| Decoder 自回归 → 可流式 | `/ai/chat/stream` 按 part 流式推送思考、正文、引用 |
| 上下文即知识 | `retrieve_knowledge` 把可见文档块拼进上下文，回答带 `sources` |
| Encoder 双向 → 适合检索 | `kh_chunk` 1024 维向量召回 + `qwen3-rerank` 精排 |
| 采样需要温度控制 | 意图分类、查询改写走低温；面向用户的正文可稍高 |
| 参数冻结 → 知识要外置 | 新文档发布走索引重建，而不是重训模型 |
| KV 缓存按前缀复用 | 多轮问答每轮重新拼检索结果，是长对话成本的重要来源 |
| Token 计费与长度上限 | 分块 512/64、历史超 12 条自动总结压缩上下文 |

一句话收尾：**三份阶段总结讲的是「把大模型接进系统」，这一篇补的是「接进来的那个东西为什么是长这样的」**——知道了它只会预测下一个 token、参数不会自己更新、上下文才是可控的知识入口，前面所有工程取舍（RAG、引用、分块、记忆分层、降级）就都能讲出理由。
