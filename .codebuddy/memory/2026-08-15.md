# 2026-08-15

## cron-job-tool 邮件发送失败排查

- 现象：JobService 报 `agent execution error: connect ETIMEDOUT 198.18.0.4:587`，邮件发送超时。
- 根因：`198.18.0.4` 是代理工具（Clash/Surge）的 Fake-IP 网段，说明本机代理以 TUN/fake-ip 模式劫持了 DNS，把 `smtp.qq.com` 解析成假 IP，而代理未正确转发 SMTP 587 流量，导致直连假 IP 超时。`nslookup` 返回真实 IP（120.233.x.x）佐证了进程内解析被劫持。
- 处理：
  - 修正 `src/app.module.ts`：删除误添加的无用 import `import { fa } from 'zod/v4/locales'`。
  - 将用户误放到 MailerOptions 顶层的 `proxy: false` 移到 `transport` 对象内（`proxy` 是 nodemailer 的 transport 选项，放顶层不生效）。
  - `npx tsc --noEmit` 通过。
- 结论提醒：`proxy: false` 只能关 HTTP 代理，**无法解决 TUN/fake-ip 的 DNS 劫持**；根治需在代理工具里对 `qq.com`/`mail.qq.com` 加 DIRECT 规则，或关闭 TUN/系统代理。
- 已确认本机代理工具为 **Clash Verge**（进程 `clash-verge` + 内核 `verge-mihomo`，混合端口 7897）。指引用户在「订阅 → 全局扩展配置 → Merge」或「编辑订阅文件 rules 段」里加 `- DOMAIN-SUFFIX,qq.com,DIRECT`，且规则须放在 `MATCH` 之前。
- 加 rules 后仍失败，进一步定位出**真正根因**（与 TUN 无关）：
  - `dns.getServers()` 返回 `["127.0.0.1"]` → Clash Verge 把系统 DNS 改成了本机（mihomo 监听 53 端口），而网卡 WLAN 的 DNS 仍是路由器 `192.168.3.1`。
  - `dns.resolve4`（c-ares）返回 fake-ip `198.18.0.4`，而 `dns.lookup`（getaddrinfo）返回真实 IP `120.232.69.34`。
  - 项目用 **nodemailer 8.0.11**，其 `shared.resolveHostname` **优先用 `dns.Resolver` 的 `resolve4/resolve6`（c-ares）**，只有解析失败才 fallback 到 `dns.lookup`。c-ares 走 127.0.0.1:53 → mihomo 返回 fake-ip → nodemailer 直连 `198.18.0.4:587` 超时。
  - 结论：`rules` 的 DIRECT 只改转发不改 DNS 解析，救不了 fake-ip。
- **最终解决方案**（根治在 Clash 侧）：
  - 方案 A（推荐）：Merge 里加 `dns.fake-ip-filter: ['+.qq.com']`，让 mihomo 对 qq.com 返回真实 IP。
  - 方案 B：关闭 Clash 的 DNS 劫持（恢复系统 DNS 为路由器/公共 DNS）。
  - 代码层无法可靠规避（填 IP 会导致 STARTTLS 证书校验失败）。
